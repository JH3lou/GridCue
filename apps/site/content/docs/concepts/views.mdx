GridCue changes how a grid looks, never the records behind it. These are the terms for that view and for changes to it.

## View State

The complete arrangement of a grid at one moment. GridCue represents it the same way for every grid library:

```ts
interface ViewState {
  visibleColumnIds: string[];
  columnOrder: string[];
  filters: FilterGroup | null; // AND of predicates such as { columnId, operator: "gt", value: 1000000 }
  sorts: SortSpec[]; // { columnId, direction: "asc" | "desc" }, primary first
  groupBy: string[]; // outermost first
  pinnedColumnIds: { start: string[]; end: string[] }; // Pinned Columns, each side in pin order
  density: "compact" | "comfortable" | "spacious";
  aggregations: AggregationSpec[]; // Totals: { columnId, function: "sum" | "avg" }, one for each column
}
```

A **Grid Adapter** translates between this shape and one grid library. `createTanStackAdapter` reads and writes TanStack Table's filter, sort, grouping, visibility, order and, when the Host says its table draws them, column pinning state. `createRowsAdapter` holds the View State itself, and `applyView(rows, state, schema)` produces the rows to render. `createQueryAdapter` holds it for rows your server fetches, and your Data Query reads it. `createAgGridAdapter` writes it into AG Grid's own filters and column state.

The view includes **pinned columns**, **density** and **totals**. GridCue writes them to the View State, and your table draws them: your own markup keeps a Pinned Column in place while the rest scroll, sets the row height, and shows the totals. An adapter lists the three operations only when you say, with its [`renders` option](/docs/api/adapters#renders), that your table does. A pin, a density change or a total the grid doesn't draw would preview, apply and change nothing the User can see, so GridCue asks instead. With the Rows Adapter, `applyView` returns `pinned` and `density` beside `columns`, and `totals`, for you to draw. A left-to-right grid reads the start as the left edge.

Your own controls keep working. A header click or a column menu changes the same View State, and the adapter reports it.

## View Operation

One atomic kind of view change. GridCue proposes these:

| Operation | Example Preview line |
| --- | --- |
| `filter.add` | Filter Market value above $1,000,000 |
| `filter.clear` | Remove the filter Market value above $1,000,000 ("Clear all filters" when none are set) |
| `sort.set` | Sort by Market value, descending |
| `group.set` | Group by Custodian, then Advisor |
| `columns.show` | Show Concentration |
| `columns.hide` | Hide Account number |
| `columns.order` | Put Advisor and Market value first |
| `columns.pin` | Pin Account number to the start, Pin Market value to the end, Unpin Advisor, or Unpin all columns |
| `density.set` | Use compact density |
| `aggregation.set` | Show the total of Market value, Show the average of Concentration, or Remove the totals |
| `limit.set` | Show only the first 10 rows, or Show every row |
| `view.reset` | Reset the view |

Clearing sorting or grouping is a `sort.set` or `group.set` with an empty list. A count is a `limit.set`: it keeps the first rows of the sorted view, and a row with no value in the first sorted column never fills it, so "top 10" on a column where only 7 rows have a value shows 7. Clearing the count is a `limit.set` with `null`. A count belongs to the view. The Rows Adapter and the TanStack Table adapter (with `renders: ["count"]`) keep the same rows for it. The Query Adapter lists a count only with [`countBeforePaging`](/docs/api/adapters#countbeforepaging), and then your Data Query must keep those rows: sort, cut to the count, then page. Changing the sort or the filters of a counted view asks before it plans anything (see [Requests](/docs/concepts/requests)).

A column is pinned once. Pinning one that is pinned to the other side moves it, and pinning a hidden column adds "Show" for it first, so the Preview says both. A hidden column keeps its pin, and shows pinned again when it is shown. "Unpin all columns" is the line when an unpin names every pinned column. A request names only the columns it changes, so a column already pinned to that side stays where it is, and a request that would change nothing says "The grid already shows this view."

## Totals

A **Total** is a sum or an average of one column: the sum of Market value, the average of Concentration. With a grouping, the grid shows each group's total. With none, it shows one total for the whole view.

- **A total counts the rows the view shows**, after its filters and its count. A row with no value in the column is skipped, and an average is the sum over the rows that have one. A group or a view with no values has an empty total, never 0.
- **A sum is exact in decimal.** The values are added as they are written, so cents never drift: 0.1 + 0.2 is 0.3, and the total doesn't depend on the order of the rows. An average is that exact sum divided once by the count, so three cells of 0.117 average 0.117. The Rows Adapter and the TanStack Table adapter use the same arithmetic, so a total over the same rows is the same number to the last digit. Their groups can still differ: see [where the adapters differ](/docs/api/adapters#where-the-two-adapters-differ).
- **A column the view groups by takes no total.** A group row shows its own value there. "Total gain" on a view grouped by Unrealized gain asks.
- **The column's kind picks the function.** A number or currency column takes a sum or an average, and a percent column takes an average only. No other kind takes a total. GridCue says which fits: "Concentration can't be totalled. Show its average instead?"
- **A column holds one total at a time.** "Average market value" on a view that shows the total of Market value replaces that total, and the Preview says so: "Show the average of Market value instead of its total". A new total on another column is added, and no total goes unless a request removes it.
- **A sort on a column with a total ranks the groups by it.** "Sort by market value, descending" on a grouped view that totals Market value puts the group with the largest total first. See [one group order](/docs/api/adapters#one-group-order-in-both-adapters).

Min, max and a count of rows are in the protocol, but no request produces them and no shipped adapter applies them.

## View Plan

An ordered set of View Operations proposed for one Utterance, tied to the Revision it was built against. It also records its status, its confidence, the evidence behind each decision, and any Clarifications or Unsupported Segments.

For "Roth accounts sorted by market value, largest first":

```json
{
  "protocolVersion": "0.1",
  "id": "plan_2",
  "baseRevision": "rows:0",
  "status": "ready",
  "operations": [
    {
      "type": "filter.add",
      "predicate": { "id": "filter_1", "type": "predicate", "columnId": "registration_type", "operator": "eq", "value": "roth_ira" },
      "combineWith": "and"
    },
    { "type": "sort.set", "sorts": [{ "columnId": "market_value", "direction": "desc" }] }
  ],
  "confidence": 0.95,
  "evidence": [
    { "key": "c0.value.registration_type", "selectedId": "roth_ira", "confidence": 1, "source": "deterministic" },
    { "key": "c0.family", "selectedId": "sort", "confidence": 0.95, "source": "provider" }
  ],
  "clarifications": [],
  "unsupportedSegments": []
}
```

(Evidence shortened.) Every evidence entry names its source: `deterministic` for code, `provider` for the Intent Provider, `host` for your schema, `user` for a Clarification answer. The plan's `confidence` is the lowest of its decisions.

A plan's `status` is one of:

- `ready`: every decision is resolved;
- `needs_clarification`: GridCue has a question, and the plan has no operations;
- `unsupported`: part of the request is outside the view or names a restricted column. It may carry operations for the Preview, but it can never apply.

## Applicable Plan

A View Plan that has passed every validation check against the current Revision and may be applied. Only `validatePlan` produces one, at runtime; a type assertion can't. Adapters refuse anything else.

Validation checks that every column exists and allows the change, every operator is legal for the column's kind and your `allowedOperators`, every enum value is approved, the adapter supports each operation, sort and group limits hold (three sorts and two group levels by default), and the resulting state is consistent. GridCue validates when it builds the Preview and again at apply. When a ready plan fails validation at Preview time, it never becomes applicable: the controller's status becomes `unsupported`, with the first issue as its message.

## Preview

The deterministic, human-readable description of exactly what a View Plan would change, shown before anything is applied. The same plan always gives the same text. It is rendered from the validated structure, not written by a model.

```ts
const { preview } = cue.getState();
preview?.lines; // ["Filter Registration type to Roth IRA", "Sort by Market value, descending"]
preview?.text; // "Filter Registration type to Roth IRA; sort by Market value, descending. No records will be changed."
```

GridCue does not auto-apply. The User applies from the Preview, or cancels.

## Revision

An identifier for one specific View State, such as `rows:3` or `tanstack:7`. It changes on every view change, including the User's own clicks.

Each plan carries its `baseRevision`. If the view changed between Preview and apply, apply is refused with "The view changed since this preview. Preview the request again." GridCue never overwrites a change it didn't see.

## New filters replace old ones

A request that filters replaces the view's current filters, just as a new sort or grouping replaces the current one. It keeps them and narrows further only when the request says so: "also", "too", "as well", "further", "only those", "of these", "among them", or "narrow it down". "Show only trusts" still switches to trusts.

The Preview names every filter a request removes, so nothing is dropped silently:

```text
Remove the filter Market value above $100,000,000
Filter Registration type to Trust
```

## A view keeps fixed dates

A relative date is worked out when the request is made, and the view keeps the two days as an ordinary filter. On 2026-11-13, "entries booked in the last 90 days" adds

```ts
{ columnId: "booked", operator: "between", value: { min: "2026-08-15", max: "2026-11-13" } }
```

The words "last 90 days" are in the plan's Preview, in brackets, and are gone once the plan is applied. The View State, the protocol and the Grid Adapter's interface hold no relative value. So a view applied today shows the same dates next month, and a saved view, an undo or a reload never means something else tomorrow. To see the last 90 days again, the User asks again. See [Dates](/docs/concepts/requests#dates) for the forms.

## Undo

Every applied plan is undoable, newest first. Each `cue.undo()` restores the exact View State from before one apply, so repeated undos step back to the starting view (up to the last 20 changes). `getState().canUndo` says whether another undo is possible.

Undo also checks the Revision. If the view changed after the apply, undo is refused ("The view changed after that update, so undo would erase newer changes"), because restoring would erase that newer change. For the same reason, a manual change between two applies ends the chain there: undo goes back to the view the User made by hand, and no further.

```ts
await cue.apply(); // "value over $100 million": canUndo is true
await cue.apply(); // "show trusts"
await cue.undo(); // back to the $100M filter, canUndo still true
await cue.undo(); // back to the starting view, canUndo false
```

Apply is atomic. If the grid fails part-way, GridCue restores the previous view when it safely can, and says which happened.
