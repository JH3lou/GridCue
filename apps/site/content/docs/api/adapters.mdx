A Grid Adapter translates GridCue's View State to one grid library. It holds no language logic: it reports the grid's current view, applies a validated View Plan all at once, restores a snapshot for undo, and tells GridCue when the view changes. GridCue ships two adapters: the Rows Adapter for rows you keep in memory, and the TanStack Table adapter.

## GridAdapter

```ts
import type { GridAdapter } from "gridcue";

interface GridAdapter {
  getSchema(): ViewSchema;
  getCapabilities(): ViewCapabilities;
  getState(): VersionedViewState;
  getDefaultState(): ViewState;
  apply(plan: ApplicableViewPlan): Promise<ApplyResult>;
  restore(snapshot: VersionedViewState): Promise<ApplyResult>;
  subscribe(listener: (state: VersionedViewState) => void): () => void;
}

type ApplyResult =
  | { ok: true; state: VersionedViewState }
  | { ok: false; code: `ADAPTER_${string}`; message: string };
```

| Method | Description |
| --- | --- |
| `getSchema()` | The `ViewSchema` for this grid. The Controller uses it unless the Host passes its own `schema`. |
| `getCapabilities()` | Which operations and limits this grid supports. See [ViewCapabilities](#viewcapabilities). |
| `getState()` | The current view and its revision. The revision must change whenever the view changes. |
| `getDefaultState()` | The view `view.reset` returns to. |
| `apply(plan)` | Applies every operation or none. Rejects plans that did not come from `validatePlan`. Resolves with `ok: true` only once the grid holds the state written, with the Revision the grid has at that moment. A grid that updates later is waited for within a bound, and `apply` throws when the bound runs out. |
| `restore(snapshot)` | Puts a saved view back. Used by undo, and to recover when `apply` throws part-way. Done, like `apply`, only once the grid holds it. |
| `subscribe(listener)` | Fires on every view change, including the User's own clicks. Returns an unsubscribe function. |

An adapter should check `isApplicable(plan)` before applying and return `ADAPTER_NOT_APPLICABLE` when it is false, and should refuse a plan whose `baseRevision` is not the current revision. `resultingState(plan)` gives the view a validated plan produces, so the adapter only has to write that state to its grid.

```ts
import { isApplicable, resultingState } from "gridcue";

async apply(plan) {
  if (!isApplicable(plan)) return { ok: false, code: "ADAPTER_NOT_APPLICABLE", message: "Only validated plans can be applied." };
  if (plan.baseRevision !== current.revision) return { ok: false, code: "ADAPTER_STALE_REVISION", message: "The view changed first." };
  return { ok: true, state: write(resultingState(plan)) };
}
```

To write your own, see [Build an adapter](/docs/guides/build-an-adapter).

## ViewCapabilities

```ts
interface ViewCapabilities {
  operations: string[];
  maxSorts?: number;
  maxGroups?: number;
  supportsAtomicApply: boolean;
  supportsSnapshotRestore: boolean;
  observesChanges: boolean;
  aggregationFunctions?: Array<"sum" | "avg" | "min" | "max" | "count">;
}
```

| Name | Type | Description |
| --- | --- | --- |
| `operations` | `string[]` | The View Operation types this grid can apply. A plan with any other type fails validation with `PLAN_OPERATION_UNSUPPORTED`, and the provider is never offered families that need it. |
| `maxSorts` | `number` | Most sort levels allowed. More gives `PLAN_CARDINALITY`. |
| `maxGroups` | `number` | Most group levels allowed. More gives `PLAN_CARDINALITY`. |
| `supportsAtomicApply` | `boolean` | Whether `apply` changes everything or nothing. When `false`, every plan fails validation with `PLAN_NOT_ATOMIC`. |
| `supportsSnapshotRestore` | `boolean` | Whether `restore` can put a saved view back. |
| `observesChanges` | `boolean` | `true` when the adapter reports manual view changes through `subscribe`. |
| `aggregationFunctions` | `string[]` | With `aggregation.set`: the total functions the grid applies. Left out, a sum and an average, which both shipped adapters apply. A total with any other function fails validation with `PLAN_AGGREGATION_KIND`. |

## MVP_OPERATIONS

```ts
import { MVP_OPERATIONS } from "gridcue";

const MVP_OPERATIONS: readonly string[] = [
  "filter.add",
  "filter.clear",
  "sort.set",
  "group.set",
  "columns.show",
  "columns.hide",
  "columns.order",
  "view.reset",
];
```

The operations every adapter supports. With no [`renders`](#renders), the TanStack Table adapter reports exactly this list, and the Rows Adapter adds `limit.set`, since its rows are all in memory and a count is exact there. An adapter whose rows come a page at a time should not list `limit.set`: GridCue then sorts alone and says the count was not applied. `columns.pin`, `density.set` and `aggregation.set` are not in `MVP_OPERATIONS`: an adapter lists each only when the Host's table draws it, and a plan that uses one the adapter doesn't list fails validation with `PLAN_OPERATION_UNSUPPORTED`.

## renders

Both adapters are headless. GridCue writes the View State, and your own markup draws it. So an adapter lists `columns.pin`, `density.set` and `aggregation.set` only when you say your table draws them:

```ts
createRowsAdapter({ schema, renders: ["pinning", "density", "totals"] });
createTanStackAdapter({ schema, table, renders: ["pinning", "density", "totals"] });
```

| Name | Lists | Your table must |
| --- | --- | --- |
| `"pinning"` | `columns.pin` | Keep the pinned columns in place at the start and the end while the rest scroll |
| `"density"` | `density.set` | Set its row height, and its cell spacing, from the View State's `density` |
| `"totals"` | `aggregation.set` | Draw each group's total and, when the view isn't grouped, one total for the view. The Rows Adapter gives them in `applyView`'s `totals` and each group's `totals`. The TanStack Table adapter needs [`gridcueAggregationFn`](#gridcueaggregationfn) registered |

- **The default is none.** With none, the adapter's capabilities are what they were, and a request to pin, unpin, change density or show a total ends in "This grid can't pin columns.", "This grid can't change its density." or "This grid can't show totals.", with no choices and nothing applied. See [Requests](/docs/concepts/requests#pins-and-density) and [Totals](/docs/concepts/requests#totals).
- **GridCue can't check it.** `renders` is a promise. A Host that names something its table doesn't draw gets a Preview, an apply and "View updated." with nothing for the User to see. Name only what you draw.
- **Columns may be pinned and totalled by default.** Every column that isn't restricted has the `pin` [capability](/docs/api/schema#column-capabilities) unless its override says otherwise, and a number, currency or percent column has `aggregate` too. Density belongs to no column.
- **Anything else throws `INPUT_CONFIG`** when the adapter is created: a name that isn't `"pinning"`, `"density"` or `"totals"`, and a value that isn't a list. So does `"count"` on the Rows Adapter, which keeps a count with no option, and `"count"` on the TanStack Table adapter, which can't list it yet. The TanStack Table adapter also throws `INPUT_CONFIG` for `"pinning"` when the table has no `setColumnPinning` (register `columnPinningFeature`), or holds its pins as `left` and `right`, as TanStack Table v8 did, instead of `start` and `end`, and for `"totals"` when it can see the table isn't set up for it: see [gridcueAggregationFn](#gridcueaggregationfn).

## createRowsAdapter

```ts
import { createRowsAdapter } from "gridcue";

function createRowsAdapter(options: RowsAdapterOptions): RowsAdapter;

interface RowsAdapterOptions {
  schema: ViewSchema;
  initialState?: ViewState;
  maxSorts?: number;
  maxGroups?: number;
  renders?: ReadonlyArray<"pinning" | "density" | "totals">;
}
```

A Grid Adapter for Hosts that keep rows in memory. It holds the View State itself; pair it with `applyView` to get the rows to render in any table.

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `schema` | `ViewSchema` | required | The schema for these rows. |
| `initialState` | `ViewState` | every schema column visible, in schema order, with no filters, sorts or groups | The starting view. It is also the view `view.reset` returns to. |
| `maxSorts` | `number` | `3` | Most sort levels allowed. |
| `maxGroups` | `number` | `2` | Most group levels allowed. |
| `renders` | `("pinning" \| "density" \| "totals")[]` | none | What your table draws, so the adapter lists `columns.pin`, `density.set` and `aggregation.set`. See [renders](#renders). |

It reports `MVP_OPERATIONS` and `limit.set`, plus what `renders` names, atomic apply, snapshot restore and `observesChanges: true`. Revisions look like `rows:0`, `rows:1`, and so on.

It never holds your rows, only the view, so it can't supply Local Values. Pass `localValues` to `createGridCue` with a function that reads your own rows: see [Local Values](/docs/api/create-grid-cue#local-values).

### RowsAdapter

```ts
interface RowsAdapter extends GridAdapter {
  setState(update: (state: ViewState) => ViewState): VersionedViewState;
}
```

`setState` is for the Host's own controls, such as clicking a column header. It receives a copy of the current View State, commits what you return, bumps the revision and notifies subscribers.

```tsx
const [{ adapter, cue }] = useState(() => {
  const adapter = createRowsAdapter({ schema, initialState });
  return { adapter, cue: createGridCue({ adapter, provider }) };
});
const { state } = useSyncExternalStore(adapter.subscribe, adapter.getState, adapter.getState);
const view = applyView(rows, state, schema);

// A header click
adapter.setState((s) => ({ ...s, sorts: [{ columnId: "market_value", direction: "desc" }] }));
```

## applyView

```ts
import { applyView } from "gridcue";

function applyView<Row extends object>(rows: readonly Row[], state: ViewState, schema: ViewSchema): ViewResult<Row>;

interface ViewResult<Row> {
  /** Visible column IDs, in display order: start-pinned columns, the others, then end-pinned columns. */
  columns: string[];
  /** The visible columns pinned to the start and to the end, each in its pin order. */
  pinned: { start: string[]; end: string[] };
  /** The row height the view asks for. */
  density: "compact" | "comfortable" | "spacious";
  /** Filtered and sorted rows. */
  rows: Row[];
  /** One for each total of the view, over every row it shows. Empty when the view has none. */
  totals: TotalValue[];
  /** Present when the view is grouped: one entry per distinct key, in the order described below. */
  groups?: Array<{ key: Record<string, Scalar>; rows: Row[]; totals: TotalValue[] }>;
}

interface TotalValue {
  columnId: string;
  function: "sum" | "avg" | "min" | "max" | "count";
  value: number | null; // null when no row holds a value, never 0
}
```

Applies a View State to in-memory rows. It is pure: it never changes `rows`, and the Host renders the result with any table. A date in a filter means the whole day in the schema's [Calendar](/docs/api/schema#calendar) time zone, which `applyView` reads from the schema; see [Build an adapter](/docs/guides/build-an-adapter#dates-are-whole-days).

- **Filters** use each column's kind. Text comparisons on `string` columns ignore case; `contains` and `startsWith` always do. `gt`, `lt`, `between` and the like never match an empty cell.
- **Sorts** apply level by level. Empty cells sort after other values in ascending order and before them in descending order.
- **Columns** are the visible column IDs in `columnOrder`, with the columns pinned to the start first and those pinned to the end last, each side in its pin order. `pinned` names them, for your table to keep in place; a hidden pinned column is in neither list and is pinned again when it is shown. `density` is the View State's, for your table to draw. They hold the View State whether or not the adapter lists the operations, so a table that draws neither can ignore them.
- **Groups** are present only when `groupBy` has columns. Each group holds its rows in sorted order, and its own `totals`. See [one group order](#one-group-order-in-both-adapters).
- **Totals** are one entry for each total in the View State, in its order, over the rows the view shows: after its filters and its count. Empty cells are skipped, a sum is exact in decimal (`0.1 + 0.2` is `0.3`), an average is that exact sum divided once by the rows that have a value, and a group or a view with no values has `value: null`, never `0`. `applyView` gives `null` for a function other than a sum or an average. `totals` is `[]` when the view has none, whether or not you set `renders`, so a table that doesn't draw totals can ignore it. `totalOf(values, "sum" | "avg")` is the same arithmetic for one list of values.

It does not paginate.

### One group order, in both adapters

A grouped, sorted view has one group order, and the Rows Adapter and the TanStack Table adapter draw the same one:

| Sort | Groups are ordered by |
| --- | --- |
| On a column with a total | That total, over the group's rows |
| On a grouping column | That column's value |
| On any other column | The order they first appear in the rows the view shows, before sorting. The sort orders the rows inside each group |

With two group levels, the groups of one outer group sit together, and each level is ordered by its own totals. Ties keep the order they first appear.

**What changed for the Rows Adapter.** It used to group the sorted rows, so a descending sort on Market value put first the group that held the largest single row. Now, with a total on Market value, the group with the largest total is first, and with no total the groups keep the order they first appear in your rows. The View State is the same, so a grouped, sorted view that requests reach today can draw its groups in a different order. TanStack Table already ordered groups this way. If you read the old order as a ranking, ask for it with a total: "total market value by advisor", then "sort by market value, descending".

### Where the two adapters differ

A shared test draws seeded views through both adapters, on rows with ties and empty cells, and compares the rows, their order, the groups, their order and every total. It passes on rows whose text cells are empty as missing cells and in one letter case. Four differences stay, and each is counted there:

- **Where a row with no value in a sorted column sits.** Both keep the same rows, in the same groups.
- **A `null` text cell in a sorted column.** TanStack's default sort can draw the text values around it out of order.
- **Letter case in a sorted text column.** TanStack's default text sort orders by code unit ("Birch" before "alder"), `applyView` as the locale does.
- **`null` and missing cells in one grouped column.** `applyView` puts them in one group, TanStack Table in two, so those groups' totals differ too. Give empty cells one shape, `null` or missing, in a column you group by.

A total on a column the view groups by would differ as well: TanStack Table shows the group's own value in that cell. GridCue never applies such a view; it asks instead, and validation refuses it. A User can still make one with the table's own controls.

## createTanStackAdapter

```ts
import { createTanStackAdapter } from "gridcue/tanstack-table";

function createTanStackAdapter(options: TanStackAdapterOptions): GridAdapter;

interface TanStackAdapterOptions {
  schema: ViewSchema;
  table: TanStackTableLike;
  maxSorts?: number;
  maxGroups?: number;
  renders?: ReadonlyArray<"pinning" | "density" | "totals">;
}
```

A Grid Adapter over a TanStack Table v9 instance. The Host keeps owning the table and its state; GridCue writes to it through the table's own setters in one batch.

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `schema` | `ViewSchema` | required | The schema, usually from `schemaFromTanStack`. |
| `table` | `TanStackTableLike` | required | A table from `useTable` or `constructTable` with the filtering, sorting, grouping, visibility and ordering features, and `columnPinningFeature` for `renders: ["pinning"]`. |
| `maxSorts` | `number` | `3` | Most sort levels allowed. |
| `maxGroups` | `number` | `2` | Most group levels allowed. |
| `renders` | `("pinning" \| "density" \| "totals")[]` | none | What your table draws, so the adapter lists `columns.pin`, `density.set` and `aggregation.set`. See [renders](#renders). |

Behavior to know:

- It reports `MVP_OPERATIONS` plus what `renders` names, atomic apply, snapshot restore and `observesChanges: true`.
- With `"totals"`, the adapter holds the totals, as it holds density, and reads them back with the rest of the View State, so undo puts them back. Register [`gridcueAggregationFn`](#gridcueaggregationfn) and `gridcueAggregationValue` so your table draws them. When the totals change, the adapter groups the rows again in the same batch, so every group row reads its new total. TanStack groups again only for a grouping array it hasn't seen, so on a grouped view the change is done only once the table holds a new one. If your state hands the table back the grouping array it had, as a shallow-equal memo does, the change fails with "The grid couldn't apply that change. Nothing was changed." rather than leave the old totals in the group rows. Pass the grouping your handler receives.
- With `"pinning"`, pins are read from and written to TanStack's own `columnPinning` state, which has GridCue's shape: `start` and `end`. A pin the User makes with the table's own controls is a view change like any other: the Revision changes and a pending Preview is refused. Without `"pinning"`, the adapter neither reads nor writes the table's pins.
- On a grouped view, TanStack's own `groupedColumnMode: "reorder"`, its default, draws the grouped columns first among the unpinned ones. `applyView` keeps every column in its place. Set `groupedColumnMode: false` on the table to draw the order `applyView` gives. Pinned columns stay where their pins put them either way.
- TanStack has no density. With `"density"`, the adapter holds it, starting at `comfortable`, and reads it back with the rest of the View State, so undo puts it back. Your table reads it from the View State and draws it.
- The default view, which `view.reset` returns to, is the table's view when the adapter is created.
- The revision (`tanstack:0`, `tanstack:1`, ...) changes only when the View State changes. Pagination, row selection, expanded rows and column sizing don't count.
- TanStack column filters combine with AND only. A plan that needs OR, or a nested filter group, fails with `ADAPTER_UNSUPPORTED_FILTER` and nothing changes.
- A column can hold a Host filter and a GridCue filter at once. GridCue stores its predicates in the column's filter value and keeps the Host's value alongside, so neither replaces the other.
- `apply` and `restore` are done only when the table holds what GridCue wrote. A table that owns its state holds it at once, so they resolve in the same tick. A table whose state the Host controls holds it on its next render, so they wait for it, up to 1,000 ms.
- A controlled slice needs a change handler that sets state at once, to exactly the value it is given. With no handler, or a handler that sets state later than 1,000 ms or stores a different value, the apply fails. See [If your app controls the table's state](/docs/guides/vite-tanstack#if-your-app-controls-the-tables-state).

```tsx
import { createGridCue } from "gridcue";
import { createTanStackAdapter, gridcueFilterFn, schemaFromTanStack } from "gridcue/tanstack-table";

const table = useTable({ features, columns, data, defaultColumn: { filterFn: gridcueFilterFn } });
const [cue] = useState(() => {
  const schema = schemaFromTanStack(table);
  return createGridCue({ schema, adapter: createTanStackAdapter({ schema, table }), provider });
});
```

## localValuesFromTable

```ts
import { localValuesFromTable } from "gridcue/tanstack-table";

function localValuesFromTable(
  table: Pick<TanStackTableLike, "getAllLeafColumns" | "getCoreRowModel">,
  columnIds: readonly string[],
): LocalValues;
```

Builds the [`localValues`](/docs/api/create-grid-cue#local-values) option from a TanStack table, so a request can name a value its rows hold. Pass it the column ids to read, which must be text columns of the schema.

```tsx
const [cue] = useState(() => {
  const schema = schemaFromTanStack(table);
  return createGridCue({
    schema,
    adapter: createTanStackAdapter({ schema, table }),
    provider,
    localValues: localValuesFromTable(table, ["advisor_name", "household"]),
  });
});
```

- **It reads every loaded row, whatever filters the table has.** It uses the table's core row model, which is the data before the table filters, sorts, groups or pages it, and it includes sub-rows. A name is found while the User's filter hides its row, so a request can name an advisor the current view doesn't show.
- **It reads what the table holds, not what the Host's server holds.** A table that pages on a server holds one page. Pass your own list of every name to `localValues` instead, as in [Local Values](/docs/api/create-grid-cue#local-values).
- **The index is kept while the table's data is.** Each function returns the same array while the table's data is the same array, so GridCue indexes it once.
- **A column id the table doesn't have throws `INPUT_CONFIG`** when you call it. `createGridCue` then checks each column against the schema and throws `INPUT_CONFIG` for one that is not an exposed, filterable text column. If the table later loses a column, the request stops with `INPUT_LOCAL_VALUES` and the view doesn't change.

## gridcueAggregationFn

```ts
import { gridcueAggregationFn, gridcueAggregationValue } from "gridcue/tanstack-table";
```

What lets a TanStack table draw the totals GridCue holds. A total is part of a column definition in TanStack, which you own, so you register two pieces once on `defaultColumn`, beside `gridcueFilterFn`, and the table needs `rowAggregationFeature`:

```ts
const table = useTable({
  features, // includes rowAggregationFeature
  columns,
  data,
  defaultColumn: {
    filterFn: gridcueFilterFn,
    aggregationFn: gridcueAggregationFn,
    getAggregationValue: gridcueAggregationValue,
  },
});
const adapter = createTanStackAdapter({ schema, table, renders: ["totals"] });
```

- **`gridcueAggregationFn`** gives each group row the sum, the average or nothing for a column, as the adapter holds it. `row.getValue(columnId)` on a group row is the total, so a sort on that column orders the groups by it, as in [one group order](#one-group-order-in-both-adapters). A group's total is over its own rows, at every level, never over its sub-groups' totals. A group with no values has no total (`undefined`).
- **`gridcueAggregationValue`** gives `column.getAggregationValue()` the column's total over every row the table shows, for a footer when the view isn't grouped.
- **A column with no total** gives `undefined`, in a group row and in the footer. A column the view groups by gives nothing in a group row.
- **The numbers match.** Both use the arithmetic `applyView` uses, so over the same rows the two adapters give the same total to the last digit. A group's rows can differ: see [where the two adapters differ](#where-the-two-adapters-differ).
- **`createTanStackAdapter` throws `INPUT_CONFIG`** when `renders` names `"totals"` and it can see a missing piece: the table has no `rowAggregationFeature`, a column the schema lets GridCue total isn't a column of the table, or one doesn't use `gridcueAggregationFn` and `gridcueAggregationValue` as its `aggregationFn` and `getAggregationValue`. Put them on `defaultColumn`, and leave them out of a column's own definition. The adapter sees the columns as they are when it is created: a column you add or redefine later isn't checked.
- **Draw them yourself.** The adapter draws nothing: your group rows and footer show the values, and your own words ("total", "avg") tell the User it isn't a row's own value.

## gridcueFilterFn

```ts
import { gridcueFilterFn } from "gridcue/tanstack-table";

function gridcueFilterFn(row: { getValue(columnId: string): unknown }, columnId: string, value: unknown): boolean;
```

A TanStack filter function that evaluates GridCue's predicates exactly as the Rows Adapter does, dates included: the adapter stores the Calendar's time zone beside a date column's kind, so both keep the same rows. Register it once with `defaultColumn: { filterFn: gridcueFilterFn }`. It passes every row for a filter value that is not GridCue's, and it does not evaluate a Host filter value stored alongside GridCue's. For a column that needs its own filter honored too, use `withGridCueFilter`.

## withGridCueFilter

```ts
import { withGridCueFilter } from "gridcue/tanstack-table";

function withGridCueFilter(fallback: FilterFn): FilterFn;
```

Wraps a column's own filter function so it keeps working alongside GridCue filters. When the column holds a GridCue filter, a row must pass GridCue's predicates and, if a Host value is stored too, the wrapped function. Otherwise the wrapped function runs as usual. The Host's value is the `host` field of GridCue's entry.

```ts
const columns = [
  { accessorKey: "advisor", filterFn: withGridCueFilter(myAdvisorFilter) },
];
```

## TanStackTableLike

```ts
interface TanStackTableLike {
  store: { state: TanStackState; subscribe(listener: () => void): { unsubscribe(): void } | (() => void) };
  _reactivity: { batch(fn: () => void): void };
  setColumnFilters(filters: Array<{ id: string; value: unknown }>): void;
  setSorting(sorting: Array<{ id: string; desc: boolean }>): void;
  setGrouping(grouping: string[]): void;
  setColumnVisibility(visibility: Record<string, boolean>): void;
  setColumnOrder(order: string[]): void;
  setColumnPinning?(pinning: { start: string[]; end: string[] }): void;
  getAllLeafColumns(): TanStackLeafColumnLike[];
  getCoreRowModel(): {
    rows: Array<{ getValue(columnId: string): unknown }>;
    flatRows?: Array<{ getValue(columnId: string): unknown }>;
  };
}
```

The parts of a TanStack Table v9 instance GridCue uses. Any table from `useTable` or `constructTable` with the filtering, sorting, grouping, visibility and ordering features fits. `setColumnPinning` is there when the table registers `columnPinningFeature`, which `renders: ["pinning"]` needs. A leaf column is `{ id, columnDef: { header?, aggregationFn?, getAggregationValue? }, getAggregationFns? }`, and `getAggregationFns` is there when the table registers `rowAggregationFeature`, which `renders: ["totals"]` needs.
