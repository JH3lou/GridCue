This guide adds GridCue to a Vite app that already renders a TanStack Table v9, such as shadcn's Data Table. The table keeps owning its state. GridCue reads and writes that state through the **Grid Adapter** for TanStack Table.

The finished version is `examples/vite` in the GridCue repo. Run it with `pnpm dev:vite`.

## Install

```bash
npm i gridcue
```

Add `@typesafe-ai/sdk` too when you turn on Jev. Only `gridcue/server` uses it.

## Enable the table features GridCue uses

GridCue changes the view: filters, sorts, grouping, and which columns show in what order. The table needs the matching features and row models:

```tsx
import {
  columnFilteringFeature,
  columnGroupingFeature,
  columnOrderingFeature,
  columnVisibilityFeature,
  createFilteredRowModel,
  createGroupedRowModel,
  createSortedRowModel,
  rowSortingFeature,
  tableFeatures,
} from "@tanstack/react-table";

const features = tableFeatures({
  columnFilteringFeature,
  rowSortingFeature,
  columnGroupingFeature,
  columnVisibilityFeature,
  columnOrderingFeature,
  filteredRowModel: createFilteredRowModel(),
  sortedRowModel: createSortedRowModel(),
  groupedRowModel: createGroupedRowModel(),
});
```

## Wire the controller

Three additions to the component that calls `useTable`:

```tsx
import { createGridCue, createRemoteProvider } from "gridcue";
import { createTanStackAdapter, gridcueFilterFn, schemaFromTanStack } from "gridcue/tanstack-table";
import { useState } from "react";

export function Accounts() {
  const table = useTable({
    features,
    columns,
    data,
    defaultColumn: { filterFn: gridcueFilterFn }, // 1. GridCue filters evaluate like the Rows Adapter's
  });

  const [cue] = useState(() => {
    // 2. A View Schema from the table's own columns
    const schema = schemaFromTanStack(table, {
      restricted: ["tax_id"],
      columns: { market_value: { kind: "currency" }, concentration: { kind: "percent" } },
    });
    // 3. The Controller: schema, adapter, and Intent Provider
    return createGridCue({
      schema,
      adapter: createTanStackAdapter({ schema, table }),
      provider: createRemoteProvider({ endpoint: "/api/gridcue" }),
    });
  });

  // …render the command bar and the table
}
```

What each piece does:

- **`gridcueFilterFn`** evaluates GridCue's filter predicates inside TanStack's filtering. Set it as the default. A column with its own `filterFn` can wrap it with `withGridCueFilter(yourFilterFn)`, so both filters keep working on that column.
- **`schemaFromTanStack(table, options)`** reads the table's leaf columns (IDs and string headers) and the first 50 rows, to infer kinds. It takes the same options as `defineSchema`, except `sampleRows`. Currency and percent can't be inferred, so declare them. If your rows load later, declare every kind, because the sample is read once, when the schema is built. See [Describe your domain](/docs/get-started/describe-your-domain) for aliases, enum values, `rowNoun`, `entity`, and `valueGroups`.
- **`createTanStackAdapter({ schema, table })`** also takes `maxSorts` (default 3), `maxGroups` (default 2) and `renders` (default none: [pins and density](#pinning-and-density), [totals](#totals)). The view at the moment you create the adapter is what "reset the view" returns to.

### Pinning and density

GridCue can pin columns and set the density, when your table draws them. The adapter lists those two operations only when you say so with `renders`, and the default is none: "pin account number" then asks "This grid can't pin columns." and changes nothing.

Name only what your table draws. For pins, register `columnPinningFeature`, and keep the pinned columns in place in your markup (with `columnSizingFeature` registered too, TanStack's `column.getStart("start")` gives each one's offset). For density, set your row height from the View State's `density`, which the adapter holds, since TanStack has none.

```tsx
import { columnPinningFeature } from "@tanstack/react-table";

const features = tableFeatures({ /* …the features above, */ columnPinningFeature });

createTanStackAdapter({ schema, table, renders: ["pinning", "density"] });
```

`renders: ["pinning"]` throws `INPUT_CONFIG` when the table has no `setColumnPinning`, so a missing `columnPinningFeature` shows up when the adapter is created. GridCue can't see whether your markup draws a pin: a Host that names one it doesn't draw gets a Preview and "View updated." with nothing to see. See [Adapters](/docs/api/adapters#renders).

### Totals

GridCue can show a total for each group, or one for the whole view when it isn't grouped ("total market value by advisor"). The adapter lists `aggregation.set` only when you say your table draws totals, and the default is none: "total market value" then asks "This grid can't show totals." and changes nothing.

Name `"totals"` only when your table draws them. Register `rowAggregationFeature`, put GridCue's two functions on `defaultColumn`, and draw the values: a group row's cell is `row.getValue(columnId)`, and a footer's is `column.getAggregationValue()`. The adapter holds the totals, so undo puts them back.

```tsx
import { rowAggregationFeature } from "@tanstack/react-table";
import { gridcueAggregationFn, gridcueAggregationValue } from "gridcue/tanstack-table";

const features = tableFeatures({ /* …the features above, */ rowAggregationFeature });

const table = useTable({
  features,
  columns,
  data,
  defaultColumn: {
    filterFn: gridcueFilterFn,
    aggregationFn: gridcueAggregationFn,
    getAggregationValue: gridcueAggregationValue,
  },
});

createTanStackAdapter({ schema, table, renders: ["totals"] });
```

`renders: ["totals"]` throws `INPUT_CONFIG` when it can see a missing piece: no `rowAggregationFeature`, or a column that doesn't use the two functions. Leave `aggregationFn` and `getAggregationValue` out of the columns' own definitions. A column you add or redefine after the adapter is made isn't checked. GridCue can't see whether your markup draws a total. See [`gridcueAggregationFn`](/docs/api/adapters#gridcueaggregationfn).

Start with the Mock Provider if you have no server yet: `provider: createMockProvider()` from `gridcue/mock`. It runs in the browser and understands your column names and declared aliases.

### Why `useState` and not `useMemo`

Create the Controller once, with a `useState` initializer. `useTable` returns a new object whenever table state changes. A `useMemo` keyed on `table` would build a new Controller after every sort, filter, or GridCue apply. The pending Preview, the undo entry, and the adapter's subscription would be lost each time.

The adapter holds on to the first table object. That is safe: it reads state through `table.store` and writes through the table's setters, which stay the same for the table's lifetime.

## Let a request name a value

Add `localValues` to the same `createGridCue` call, and "Avery Lane's accounts" filters Advisor to that advisor, while "the Alder household" filters Household. `localValuesFromTable` reads the values from the table's own rows:

```tsx
import { createTanStackAdapter, gridcueFilterFn, localValuesFromTable, schemaFromTanStack } from "gridcue/tanstack-table";

return createGridCue({
  schema,
  adapter: createTanStackAdapter({ schema, table }),
  provider: createRemoteProvider({ endpoint: "/api/gridcue" }),
  localValues: localValuesFromTable(table, ["advisor_name", "household"]),
});
```

- **It reads every loaded row, whatever filters the table has.** A request can name an advisor whose rows the current filter hides. It includes sub-rows, and it reads the rows when a request is made, so rows that load later are found.
- **Name the columns that hold names,** such as an advisor or a household. Each must be a text column of the schema that is not restricted, and a column id the table doesn't have throws `INPUT_CONFIG`.
- **Keep `data` the same array between renders.** The index is kept while the table's data is the same array. A `data` that is a new array on every render makes GridCue index it again on every request.
- **A table that pages on a server holds one page.** Pass `localValues` your own list of every name instead of `localValuesFromTable`.
- **The values are read in the browser and never sent.** The endpoint gets the same request with `localValues` on or off. A name the User types is in the request. See [Safety and protocol](/docs/safety#the-data-boundary).

See [Requests](/docs/concepts/requests#local-values) for what reads and what asks, and [`localValuesFromTable`](/docs/api/adapters#localvaluesfromtable) for the reference.

## If your app controls the table's state

Many apps pass `state: { sorting }` and `onSortingChange` to the table, to keep the view in a store or the URL. GridCue works with that, with three rules.

**Every slice you control needs its change handler.** GridCue writes the filters, sorting, grouping, column order, and column visibility, then waits for the table to hold what it wrote. A controlled slice with no handler never changes, so the table can't hold it. After 1,000 ms the apply fails. When the request changed only that slice, nothing is changed and the command bar says "The grid couldn't apply that change. Nothing was changed." When it also changed a slice the table owns, GridCue puts that slice back and says "The grid couldn't apply that change. The previous view is back."

**Store exactly what the handler is given.** GridCue waits for the very value it wrote. A handler that changes it, for example by adding a tiebreaker sort or keeping only one sort, never stores that value. After 1,000 ms the apply fails, and the command bar says the view changed meanwhile. The table keeps the handler's value, and the User can't undo it. Adjust the value where you read it, such as in your fetch, not in the handler.

**Set the state first, and fetch after.** The wait ends when the table renders the new state. A handler that sets state right away, then starts a fetch, is fine:

```tsx
const [sorting, setSorting] = useState<SortingState>([]);

const table = useTable({
  features,
  columns,
  data,
  state: { sorting },
  onSortingChange: (updater) => {
    setSorting(updater); // 1. set the state now
    void refetchRows(); // 2. then fetch
  },
});
```

A handler that waits for its fetch before it sets state makes the apply fail. If the state is set later than 1,000 ms, the apply has already failed and the command bar says so, but the table still takes GridCue's change when the state lands. That change isn't undoable, and the message no longer matches the table. Undo waits the same way.

A table that owns its state needs none of this. Apply returns at once, as before.

If the User changes the view while GridCue waits and the apply then fails, GridCue keeps the User's change and doesn't undo it.

## Pick a command bar

Two UIs sit on the same `useGridCue` hook. Pick one.

**The shadcn `CommandBar`**, for apps that already use shadcn/ui and Tailwind. You copy the source into your app and own it:

```bash
npx shadcn@latest add https://gridcue.dev/r/command-bar.json
```

```tsx
import { CommandBar } from "@/components/gridcue/command-bar";

<CommandBar controller={cue} />
```

It installs `command-bar.tsx`, `preview-panel.tsx`, and `clarification-prompt.tsx`, and depends on shadcn's `button`, `input`, `card`, and `badge`. `examples/vite` uses this one. See [Command bar](/docs/components/command-bar).

**The built-in `GridCueBar`**, for any React app, with no Tailwind. It is styled with plain CSS:

```tsx
import { GridCueBar } from "gridcue/react";
import "gridcue/styles.css";

<GridCueBar controller={cue} />
```

It takes `label`, `placeholder`, and `className`. See [GridCueBar](/docs/components/grid-cue-bar).

Both show the Preview before anything applies, ask Clarifications, offer undo, cancel on Escape, and apply a ready Preview with Ctrl+Enter or Cmd+Enter.

## Mount the endpoint in Vite's dev server

`createRemoteProvider` posts to `/api/gridcue`. In development, mount the **Server Handler** as Vite middleware. First, a small module that picks the provider on the server:

```ts
// gridcue-api.ts
import { createMockProvider } from "gridcue/mock";
import { createGridCueHandler, createJevProvider, toNodeHandler } from "gridcue/server";

/** Jev when JEV_API_KEY is set on the server, the Mock Provider otherwise. */
export const gridcueApi = (env: Record<string, string | undefined>) => {
  const provider = env.JEV_API_KEY ? createJevProvider({ apiKey: env.JEV_API_KEY }) : createMockProvider();
  return { listener: toNodeHandler(createGridCueHandler({ provider })) };
};
```

Then a plugin in `vite.config.ts` that mounts it in both `vite dev` and `vite preview`:

```ts
// vite.config.ts
import react from "@vitejs/plugin-react";
import { defineConfig, loadEnv, type Plugin } from "vite";
import { gridcueApi } from "./gridcue-api.ts";

const gridcue = (env: Record<string, string>): Plugin => {
  const api = gridcueApi(env);
  const mount = (server: { middlewares: { use(path: string, fn: typeof api.listener): unknown } }): void => {
    server.middlewares.use("/api/gridcue", api.listener);
  };
  return { name: "gridcue-api", configureServer: mount, configurePreviewServer: mount };
};

export default defineConfig(({ mode }) => ({
  plugins: [react(), gridcue(loadEnv(mode, process.cwd(), ""))],
}));
```

`loadEnv` with an empty prefix reads `JEV_API_KEY` from `.env.local` into the config, which runs in Node. Vite exposes only `VITE_`-prefixed variables to the browser, so keep the key's name unprefixed.

<Callout type="warn">
Import `gridcue/server` only from `vite.config.ts` and other server files, never from `src/`. In a browser build it throws on import.
</Callout>

## In production

Vite's dev middleware does not exist in a production build. Serve the built `dist/` from a server that also mounts the handler. `examples/vite/server.ts` does it with Express:

```ts
import express from "express";
import { gridcueApi } from "./gridcue-api.ts";

const app = express();
app.post("/api/gridcue", gridcueApi(process.env).listener);
app.use(express.static("dist"));
app.listen(4173);
```

Put the endpoint behind your app's auth and rate limits first: see [Protect the endpoint](/docs/guides/protect-the-endpoint). Other runtimes are in [Server Handler recipes](/docs/guides/server-handler).

## Limits of the TanStack adapter

TanStack column filters combine with AND only. A plan that needs OR or a nested filter group fails with `ADAPTER_UNSUPPORTED_FILTER`, and nothing changes. See [Adapters](/docs/api/adapters).
