title: Rows on a server
description: Keep the rows GridCue would keep when your own Data Query fetches them. Pick the adapter, build the query from the View State, and prove it with the Query Check.
---

Use this guide when your rows live on a server and your table shows one page at a time. GridCue gives you a View State. You turn it into your own **Data Query** and fetch the rows.

**GridCue never writes the Data Query.** It produces no SQL, no ORM calls and no request parameters. Your server owns your data and how it is fetched. What GridCue gives you instead is a table of what each filter means, and a [Query Check](/docs/api/testing) that runs that table against your query.

The finished version is the `/paged` page of `examples/next`, with its route in `examples/next/app/api/rows`. It loads the synthetic wealth rows into an in-memory SQLite database (`node:sqlite`, so no dependency) and pages through them. Run it with `pnpm dev:next`, then open `http://localhost:3100/paged`.

## 1. Pick the adapter

| Your grid | Adapter |
| --- | --- |
| TanStack Table with `manualPagination`, `manualFiltering` or `manualSorting` | The [TanStack Table adapter](/docs/api/adapters#createtanstackadapter), as before. It lists no count, since a table that pages on a server holds one page |
| Any other table | The [Query Adapter](/docs/api/adapters#createqueryadapter) |
| A grid with no adapter yet | [Build an adapter](/docs/guides/build-an-adapter) |

Don't use the Rows Adapter for rows on a server. It always lists `limit.set`, so a Host that ignores the count shows every row under a Preview that says ten.

## 2. Build the Data Query from the View State

Build the query from `adapter.getState().state` on every change, never from the grid's own model, for everything the View State holds. The Query Adapter's subscription fires when the View State changes, whether GridCue, an undo or your own header click changed it.

```tsx
const view = useSyncExternalStore(adapter.subscribe, adapter.getState, adapter.getState);
// Refetch when view.state changes. Loading and fetch errors are yours.
```

On the TanStack Table adapter, the table's `columnFilters` wrap GridCue's predicates, so read the View State, not the table's filters.

A filter GridCue can't read is not in the View State: a global filter, or your own custom filter on a column. It is still yours. Your Data Query is the View State's filters and your own, joined with "and". A query built from the View State alone would return rows your own filter control says are filtered out.

## 3. What each filter means

This is what `applyView` and `matchesPredicate` do today. A Data Query that copies it keeps the rows GridCue would. In this table an "empty cell" is `null`, a missing value or `""`.

| View State | Keeps | Leaves out | A Data Query that copies it naively |
| --- | --- | --- | --- |
| `neq "x"` (text, number, enum) | every row whose cell isn't `x`, **including empty cells** | rows equal to `x` | SQL `<>` drops `NULL` rows |
| `eq`, `in` on a text column | equal **ignoring case**, not accents: "Zoë" isn't "Zoe" | empty cells | SQL `=` is case-sensitive in some databases, and ignores accents in others (MySQL 8's default collation). A Swedish or Finnish collation that ignores accents keeps å, ä and ö apart and still reads é as e |
| `eq`, `in` on an enum, number or yes/no column | exactly equal | empty cells | |
| `contains`, `startsWith` | ignoring case, always, but not accents | empty cells | `LIKE` case and accent rules vary by database, and `%` and `_` in the value are plain text here |
| `gt`, `gte`, `lt`, `lte` | as written | empty cells | |
| `between {min, max}` | **both ends included** | empty cells | an exclusive range drops the ends |
| `isEmpty` | `null`, missing, `""` | everything else, **including whitespace-only text** | a "blank" test that trims text keeps whitespace-only text |
| `isNotEmpty` | everything but those | empty cells | |
| `and`, `or` groups | each as nested in the View State | | a missing bracket around an `or` inside an `and` |
| A count (`limit`) | the first N rows of the sorted, filtered rows, before grouping | the rest, and **a row with no value in the first sorted column** | a cut after paging keeps the first N of one page |

More rows of the same table:

- **An empty operand follows the same rules.** `eq ""` and `in [""]` keep exactly the empty cells. `neq ""` leaves them out. `contains ""` and `startsWith ""` keep every row, empty cells included.
- **A date means the whole day** on a date or date-and-time column, in the schema's Calendar time zone. `eq 2026-03-08` keeps every instant from that day's midnight to the next, in that zone. `gt` leaves out the whole day, `gte` includes it, and `between` includes both days whole. A cell with a time and an offset is the day that instant falls on in the zone. A cell with a time and no offset is on its own date. With no `timeZone` in the Calendar, GridCue uses the browser's, which a server can't know: [name a time zone](/docs/api/schema#calendar) so both sides agree.
- **A count never keeps an empty cell in the first sorted column.** "Top 10 by market value" shows seven rows when only seven have a market value. `NaN` counts as no value.
- **Rows that tie are yours to order.** A database has no load order, so rows that tie on every sorted column may come in any order. Break ties by a unique column, such as the row's own key, so two pages never repeat or skip a row. In `applyView` today they keep the order they were loaded in. GridCue doesn't promise that as a rule.
- **A count at a tie keeps any of the tied rows.** When "top 10" cuts inside a run of rows with the same value, your query may keep any of the tied rows for its last places. It must keep every row ahead of the tied value, none behind it, and ten rows in all. `RANK() <= 10` and `FETCH FIRST 10 ROWS WITH TIES` keep every tied row, which is more than ten, and the Query Check fails them.
- **Where empty cells sort is yours, inside a rule.** In `applyView` today, a cell that is `null` or missing comes last going up and first going down, and `""` sorts as the shortest text. GridCue doesn't promise that, so `NULLS FIRST` and `NULLS LAST` both pass the Query Check, on any column in any direction. The rule: a row is placed by its leading sorted columns that hold a value, up to its first empty one. A row with a value in the first sorted column and none in the second sits among the rows that share its first value, first or last. `ORDER BY (a IS NULL OR b IS NULL), a, b` moves it past rows with another first value, and fails, with a count or without. A row with no value in the first sorted column may sit anywhere.
- **Text sorts by its letters, ignoring case,** not by its length first. The Query Check checks the order only between texts made of the letters A to Z that their letters tell apart. Where a space, a digit, a mark or an accented letter sorts against a letter is your collation's own, so a collation that skips spaces passes too. Rows that hold the very same text tie on it, whatever its characters, so the next sort orders them.
- **An enum sorts by its values' IDs, as text,** not by its labels, and not in the order its values are declared. A database's own enum type sorts in declared order, so sort its column as text.
- **Every sort holds, whatever else the view does.** A second sort orders the rows that tie on the first, on a text or enum column too, each way, and each later sort the rows that tie on the sorts before it, in a count as well. Every sort, in its own direction, and the count still hold beside a filter or an "or" group, and where a column is hidden. Build the sorts and the count one way for every View State. The Query Check puts each rule about sorting and counting beside each kind of filter: each operator, a filter on the first sorted column, two filters joined with "and", each "or" group, and a filter on a hidden column, with the first sort each way. So a query that uses `RANK()`, cuts by the first sort alone, or drops or turns a sort only beside an "equals" filter, only where the filters hold an "or", only where a column is hidden, or only when the first sort goes up, fails. With no filter it also sorts and counts by each column in turn, text and enum columns too, and by two, three and four columns, so a query that is wrong only when one column is sorted first, or only for one number of sorts, fails as well. It promises those pairs and no more: a query that is wrong only where three such things meet, such as a count beside an "equals" filter on a hidden column, can pass.
- **Hiding a column never changes which rows or what order.** A filter or sort on a hidden column still holds, inside an "or" or "and" group too, and so does a later sort on one. A count still sorts by a hidden column.

## 4. Never put a value or a column name into query text

- **Values are parameters.** A value from the View State is bound with `?`, never joined into the query text.
- **Column IDs are checked against the schema.** Look the ID up in your View Schema before you use it as an identifier, and refuse an unknown one. Never use a restricted column.
- **Refuse a View State too large for your database.** A View State sets no limit on how deep its filter groups nest, how many filters it holds, how long a list is, or how many sorts it holds, and a database does. The example answers 400 past 16 groups deep, 200 filters or a list of 1,000 values, and reads the request in a `try`, so a body nested too deep to read is a 400 too, never a 500.
- **Refuse a column sorted twice.** A second sort on a column says nothing its first sort didn't, and SQLite refuses an `ORDER BY` of thousands of terms. The example answers 400 for a column sorted twice, so its sorts are never more than its columns.

## 5. Run the Query Check in your tests

[`queryCheck`](/docs/api/testing) builds synthetic rows and View States from your schema, with the rows GridCue keeps for each. Load the rows into a test database, run each state through your own query, and compare the ids. See [Run it in a test](#run-it-in-a-test) below.

## 6. `countBeforePaging` only when your server sorts, cuts, then pages

Pass `countBeforePaging: true` to the Query Adapter only when your server sorts, keeps the first N rows, and only then pages. The adapter then lists `limit.set`, and "top 10" is the true first ten. With the default, GridCue sorts and says "Count not applied: this grid can't show only the first 10". See [countBeforePaging](/docs/api/adapters#countbeforepaging).

## 7. Loading, errors and the number of rows are yours

GridCue shows no loading state for a fetch, and it doesn't know whether the rows arrived. Show your own loading and error states, and the number of rows your server counted. A view can change over rows that then fail to load, which GridCue can't see.

## A worked example

Everything below is **the Host's code**, from `examples/next`. It isn't GridCue's, and GridCue ships none of it. Copy it, change it, and run the Query Check against your copy.

The page creates the adapter, with a count that is cut before paging and no grouping, since a page can't be grouped by the table alone:

```tsx
// examples/next/app/paged/paged-view.tsx
const adapter = createQueryAdapter({ schema, initialState: wealthInitialState, countBeforePaging: true, without: ["group.set"] });
const cue = createGridCue({ adapter, provider: createRemoteProvider({ endpoint: "/api/gridcue" }) });
const view = useSyncExternalStore(adapter.subscribe, adapter.getState, adapter.getState);
const { state, revision } = view;
```

It refetches on every change of the View State and its Revision, of the page, or a retry, and it cancels a fetch the next change makes stale:

```tsx
useEffect(() => {
  const controller = new AbortController();
  setLoading(true);
  loadRows(state, page, controller.signal).then(/* set the rows, or the error */);
  return () => controller.abort();
}, [state, revision, page, attempt]);
```

The route's query code turns the View State into SQL. The text is fixed. The values are bound:

```ts
// examples/next/app/api/rows/query.ts
case "neq":
  // GridCue's "is not" keeps empty cells. SQL's <> alone would drop them.
  params.push(bound(column, value));
  return text ? `${cell} <> ?` : `(${c} IS NULL OR ${c} <> ?)`;
case "contains":
  // instr, not LIKE: % and _ in the value are plain text, and empty text keeps every row.
  params.push(bound(column, value));
  return `instr(${cell}, ?) > 0`;
case "between": {
  // Both ends included.
  const range = rangeOf(value);
  params.push(bound(column, range.min), bound(column, range.max));
  return `(${c} >= ? AND ${c} <= ?)`;
}
```

The column ID is checked against the schema before it becomes an identifier. An unknown or restricted column is an error, and the ID is never put in the message:

```ts
const usableColumn = (schema: ViewSchema, columnId: unknown, use: "filter" | "sort"): ColumnDescriptor => {
  const column = schema.columns.find((c) => c.id === columnId);
  // The ID is not put in the message: it came from the request.
  if (!column) throw new DataQueryError(`A ${use} names a column this grid doesn't have.`);
  if (column.sensitivity === "restricted") throw new DataQueryError(`A ${use} names a restricted column.`);
  if (!column.capabilities.includes(use)) throw new DataQueryError(`${column.label} can't be used to ${use}.`);
  return column;
};
```

## Run it in a test

`gridcue/testing` imports no test runner, so it runs under Vitest, Jest or a plain script. This is the loop from `examples/next/app/api/rows/query.test.ts`, cut to its core:

```ts
import { createQueryAdapter } from "gridcue";
import { queryCheck } from "gridcue/testing";

const operations = createQueryAdapter({ schema, countBeforePaging: true }).getCapabilities().operations;
const check = queryCheck(schema, { id: "account_number", operations });
const db = openRowsDatabase(schema, check.rows); // your test database, loaded with the synthetic rows

for (const c of check.cases) {
  const { rows } = readRows(db, schema, c.state, { offset: 0, size: check.rows.length }); // your own query
  const result = c.compare(rows.map((row) => row.account_number));
  if (!result.ok) throw new Error(result.message);
}
```

Read each case twice, once in one page and once in small pages, so a count cut after paging fails too. A failure names the rule it tests, the view in words, and the ids that are missing or extra. This one came from a query that wrote "is not" as SQL `<>`, on a small schema with a Custodian text column:

```text
not equal keeps empty cells, and ignores case on text (Custodian is not “åLDER fen”): 4 rows missing, ids 33, 34, 51 and 57; 8 rows extra, ids 17, 22, 27, 28, 46, 49, 54 and 64
```

A count that returns the wrong number of rows says how many came back and how many the count asks for. Rows out of order name the first row out of place. The [Testing](/docs/api/testing#compare) page shows both, and lists what is yours to choose.

The Query Check only helps a Host that runs it, and it tests the meanings core holds when it runs. Run it on every schema you serve, and again when you change the query or upgrade GridCue.
